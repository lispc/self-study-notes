# 单周期与五级流水 RISC-V 处理器

> 本书位置：数字电路设计 · 第四部分（造一颗 CPU）· 第 14 章
> 前置知识：第 4 章（触发器与时序约束）；第 5 章（有限状态机）；第 6 章（同步设计与关键路径）；第 7 章（可综合 Verilog）；第 9 章（STA）；第 10 章（加法器与 ALU 的代价）；第 12 章（寄存器堆与存储结构）。
> 学习目标：认识 RV32I 的指令格式与"load-store"设计哲学；能从零画出单周期 RISC-V 处理器的数据通路，说清每个多路选择器存在的理由；会用主译码器/ALU 译码器两级真值表推出全部控制信号；逐拍跟踪 add、lw、sw、beq 四条指令；说清单周期方案的病根（时钟周期由最慢指令决定）；理解五级流水如何用流水线寄存器把吞吐量提上去，并算清"理想 5 倍、实际 2–4 倍"的账。

## 1. 一句话总结

**一颗 CPU = 一条数据通路（PC、指令存储器、寄存器堆、ALU、数据存储器）+ 一张控制真值表。单周期实现让每条指令在一个时钟周期内走完整条通路，简单到极点，也因此被最慢的 lw 指令拖死；五级流水把通路切成 IF/ID/EX/MEM/WB 五段，段间插触发器，五条指令像流水线工件一样同时在厂，吞吐量由最慢的那一段决定——这就是从"一条指令一台机器"到"五条指令共享一台机器"的跨越，代价是流水线寄存器的开销和一类全新的麻烦：冒险。**

先把指令集看清楚，再动手造机器。

## 2. RV32I 速览：为硬件而生的指令集

RISC-V 的设计目标是"让实现者舒服"。RV32I（32 位基础整数集）只有约 40 条指令，几条纪律贯穿始终：

- **32 个通用寄存器** `x0`–`x31`，每个 32 位；`x0` 硬连线为 0（读恒 0、写无效）——省掉无数特殊情况。
- **load-store 架构**：运算指令的源和目的只能是寄存器；内存只能由 `lw`（load word）和 `sw`（store word）触碰。于是 ALU 和数据存储器永远不在同一条指令里串联之外的组合出现，数据通路极其规整。
- **定长 32 位指令，六种格式**。本章用到四种：

| 格式 | 布局（高位 → 低位） | 用途 |
|---|---|---|
| R | funct7 · rs2 · rs1 · funct3 · rd · opcode | 寄存器-寄存器运算（add 等） |
| I | imm[11:0] · rs1 · funct3 · rd · opcode | 立即数运算、load |
| S | imm[11:5] · rs2 · rs1 · funct3 · imm[4:0] · opcode | store |
| B | imm[12, 10:5] · rs2 · rs1 · funct3 · imm[4:1, 11] · opcode | 条件分支（beq 等） |

三种格式的字段**故意对齐**：`rs1`、`rs2`、`rd` 永远在同一比特位置，于是寄存器堆可以在译码完成前就开始读（读错了大不了不用）；opcode 永远在低 7 位。立即数字段看似在 S/B 格式里被拆散了，但拆的方式让"立即数生成器"只是几组固定连线——这些都是为硬件省晶体管的设计，不是美学洁癖。

本章的指令子集：

| 指令 | 语义 | 格式 |
|---|---|---|
| `add rd, rs1, rs2` | rd ← rs1 + rs2 | R |
| `addi rd, rs1, imm` | rd ← rs1 + imm（符号扩展） | I |
| `lw rd, imm(rs1)` | rd ← Mem[rs1 + imm] | I |
| `sw rs2, imm(rs1)` | Mem[rs1 + imm] ← rs2 | S |
| `beq rs1, rs2, imm` | 若 rs1 = rs2 则 PC ← PC + imm | B |

## 3. 单周期处理器

### 3.1 数据通路：一条从 PC 到写回的长链

单周期设计的规则只有一条：**每条指令在一个时钟周期内完成**，所以数据通路是纯粹的组合逻辑长链，两端是状态元件（PC 寄存器、寄存器堆、存储器）。跟着指令流动的方向，需要的部件依次是：

```
        ┌────┐   ┌─────────┐   ┌──────────┐   ┌─────┐   ┌─────────┐
 PC ──▶ │ PC │──▶│ 指令存储器│──▶│ 译码+立即数│──▶│ ALU │──▶│ 数据存储器│──┐
  ▲     └────┘   └─────────┘   │ 寄存器堆读 │   └─────┘   └─────────┘  │
  │                            └──────────┘        │                  │
  │              分支目标 = PC+imm ◀── 零标志 ◀─────┘        写回数据 ◀──┘
  └────── 下一PC = PC+4 或分支目标（多选器）
```

四个**多路选择器**，每一个都对应一类指令的差异化需求：

1. **ALU 第二源**：R 型指令用 `rs2` 的读数，I/S/B 型用立即数——选一。
2. **写回数据源**：`lw` 写回存储器读出的字，运算指令写回 ALU 结果——选一。
3. **下一 PC**：顺序执行取 PC+4，分支成立取 PC+imm——选一。
4. （寄存器堆写地址恒为 `rd`/`rs2` 字段直连，不需要选。）

ALU 本身第 10 章已经备好：一个快速加法器加与/或/比较电路。注意 `beq` 判断"相等"用 ALU 做减法看零标志，不另造比较器——硬件复用是 CPU 设计的第一本能。

### 3.2 控制器：两级译码，两张真值表

控制器的输入是指令的 opcode（加 funct 字段），输出是全部多选器选择信号和写使能。标准做法是拆成两级：

**主译码器**（看 opcode，7 位）：

| 指令 | RegWrite | ALUSrc | MemWrite | MemtoReg | Branch | ALUOp |
|---|---|---|---|---|---|---|
| `add`（R 型） | 1 | 0 | 0 | 0 | 0 | 10 |
| `addi` | 1 | 1 | 0 | 0 | 0 | 10 |
| `lw` | 1 | 1 | 0 | 1 | 0 | 00 |
| `sw` | 0 | 1 | 1 | — | 0 | 00 |
| `beq` | 0 | 0 | 0 | — | 1 | 01 |

**ALU 译码器**（看 ALUOp + funct3/funct7）：ALUOp = 00 一律做加（算地址）；01 做减（判等）；10 时查 funct3（`add`/`sub` 再靠 funct7 第 5 位区分）。

为什么不直接一张大真值表？因为两级各自很小：主译码器 7 输入、ALU 译码器 4–5 输入，综合出来都是几级与或门；合成一张则要处理 opcode + funct3 + funct7 的完整空间。更重要的是**分工对应结构**：ALUOp 是"这类指令要 ALU 干什么"的摘要，类内细节下放给第二级——这个分层让新增指令（比如 `xor`）只动 ALU 译码器一行。

落成 SystemVerilog 就是第 5 章练过的填表活：

```verilog
// 主译码器：RV32I 核心子集
always_comb begin
    reg_write = 1'b0;  alu_src = 1'b0;  mem_write = 1'b0;
    mem_to_reg = 1'b0; branch  = 1'b0;  alu_op    = 2'b00;
    unique case (opcode)
        7'b0110011: begin reg_write = 1'b1;                alu_op = 2'b10; end // add/sub/...
        7'b0010011: begin reg_write = 1'b1; alu_src = 1'b1; alu_op = 2'b10; end // addi
        7'b0000011: begin reg_write = 1'b1; alu_src = 1'b1;
                          mem_to_reg = 1'b1;               alu_op = 2'b00; end // lw
        7'b0100011: begin alu_src = 1'b1;  mem_write = 1'b1; alu_op = 2'b00; end // sw
        7'b1100011: begin branch  = 1'b1;                    alu_op = 2'b01; end // beq
        default: ;
    endcase
end
```

### 3.3 四条指令各走一遍

- **`add x5, x6, x7`**：PC 取出指令 → 译码读出 `x6`、`x7` → ALUSrc = 0 选寄存器数 → ALU 加 → MemtoReg = 0 写回 ALU 结果 → RegWrite = 1 写入 `x5` → PC ← PC+4。
- **`lw x5, 40(x6)`**：读 `x6` → ALUSrc = 1 选立即数 40 → ALU 加出地址 → 数据存储器读 → MemtoReg = 1 写回存储器数据。它是唯一**走完全部五个部件**的指令——记住这一点，第 3.4 节要考。
- **`sw x7, 40(x6)`**：同 `lw` 算出地址，但 MemWrite = 1 把 `x7` 的值写进存储器，RegWrite = 0。写回多选器的输出无人使用。
- **`beq x6, x7, 16`**：两个寄存器进 ALU 做减法；零标志为 1 且 Branch = 1 时，下一 PC 多选器切到 PC+16。

### 3.4 单周期的病根：所有人陪最慢的走

第 6 章的纪律在这里露出獠牙：全片一个时钟，周期必须容纳**最慢的一条指令**。给一组延迟参数（触发器 $t_{pcq} = 0.05$、$t_{setup} = 0.05$，指令存储器 0.20，寄存器堆读 0.15，ALU 0.20，数据存储器 0.25，多选器忽略），各指令的关键路径是：

| 指令 | 路径 | 延迟 (ns) |
|---|---|---|
| `add` | PC → 指令存储 → 寄存器堆 → ALU → 写回 | 0.05+0.20+0.15+0.20+0.05 = 0.65 |
| `beq` | 同上（ALU 判零 → PC 多选） | 0.65 |
| `sw` | …→ ALU → 数据存储写 | 0.85 |
| `lw` | …→ ALU → 数据存储读 → 写回 | 0.90 |

于是时钟周期被钉死在 $T_c = 0.90$ ns，$f_{max} \approx 1.1$ GHz——`add` 明明 0.65 ns 就能算完，却也只能每 0.90 ns 来一条。三种浪费一目了然：

- **指令间不平衡**：快指令陪 lw 慢跑；
- **部件闲置**：ALU 在 lw 的访存阶段闲着，存储器在 add 的全程闲着，每个部件实际利用率只有几分之一；
- **无法复用**：每条指令独占所有硬件一整拍，吞吐量的天花板就是 $1/T_c$。

补一刀：想给单周期机加乘法指令？那就在关键路径上串一个 $O(\log n)$ 的乘法器，**所有**指令的周期跟着变长——这就是为什么真实 ISA 的乘除法要么是多周期、要么在流水线上分几拍完成。

## 4. 五级流水处理器

### 4.1 切法：五个站，四个流水线寄存器

流水的想法朴素得像工厂：把长链在自然的部件边界上切成五段，段与段之间插触发器——**流水线寄存器**。

| 站 | 名字 | 干什么 |
|---|---|---|
| IF | Instruction Fetch | PC 取指，算 PC+4 |
| ID | Instruction Decode | 译码、读寄存器堆、生成立即数 |
| EX | Execute | ALU 运算 / 算地址 / 判分支 |
| MEM | Memory | 数据存储器读写 |
| WB | Write Back | 结果写回寄存器堆 |

四个流水线寄存器 IF/ID、ID/EX、EX/MEM、MEM/WB 各保存"一条指令走到这里时的全部中间结果"。写法和第 4 章的寄存器没有任何区别：

```verilog
// ID/EX 流水线寄存器：数据、控制信号一起随车走
always_ff @(posedge clk) begin
    id_ex_pc4    <= if_id_pc4;
    id_ex_rd1    <= rf_rd1;
    id_ex_rd2    <= rf_rd2;
    id_ex_imm    <= if_id_imm;
    id_ex_rd     <= if_id_instr[11:7];   // 目标寄存器号也要带走
    // 控制信号同样逐级传递：RegWrite/MemtoReg 要到 WB 才用，
    // MemWrite 到 MEM 才用——各站的"说明书"随指令一起流水
    id_ex_ctl    <= id_ctl;
end
```

一个容易漏的细节：指令本身是流动的，**它需要的控制信号也得跟着走**。WB 站才用的 RegWrite、MEM 站才用的 MemWrite，都必须在 ID 译出后逐级寄存下去——控制信号就是贴在工件上的工序卡。

### 4.2 时空图与加速比的账

五条独立指令流入流水线：

| 拍 | IF | ID | EX | MEM | WB |
|---|---|---|---|---|---|
| 1 | `lw` | | | | |
| 2 | `add` | `lw` | | | |
| 3 | `sub` | `add` | `lw` | | |
| 4 | `or` | `sub` | `add` | `lw` | |
| 5 | `and` | `or` | `sub` | `add` | `lw` |
| 6 | … | `and` | `or` | `sub` | `add` |

第 5 拍起流水线灌满，五个部件**全部在干活**，每拍有一条指令流出。吞吐量不再由"整条长链"决定，而由**最慢的一站**决定。用第 3.4 节的参数算各站延迟（含流水线寄存器的 $t_{pcq}$ 与下游 $t_{setup}$）：

| 站 | 内容 | 延迟 (ns) |
|---|---|---|
| IF | $t_{pcq}$ + 指令存储 + $t_{setup}$ | 0.30 |
| ID | $t_{pcq}$ + 寄存器堆读 + $t_{setup}$ | 0.25 |
| EX | $t_{pcq}$ + ALU + $t_{setup}$ | 0.30 |
| MEM | $t_{pcq}$ + 数据存储 + $t_{setup}$ | 0.35 |
| WB | $t_{pcq}$ + $t_{setup}$ | 0.10 |

时钟周期 $T_c = 0.35$ ns（MEM 站决定），$f_{max} \approx 2.9$ GHz，理想吞吐量是单周期的 $0.90/0.35 \approx 2.6$ 倍。两个"为什么不是 5 倍"的理由：

- **站间不平衡**：WB 站 0.10 ns 的潜力被 MEM 站 0.35 ns 浪费掉——流水线的效率上限是 $n$ 段中"最长段"与"平均段"之比；
- **流水线寄存器税**：每段都付了 $t_{pcq} + t_{setup} = 0.10$ ns 的固定开销。段切得越多，税占的比例越大——这就是为什么真实高性能处理器是 10–20 级而不是 1000 级。

另外注意区分两个指标：单条指令的**延迟**反而变长了（5 拍 × 0.35 = 1.75 ns > 0.90 ns），流水线提升的是**吞吐量**。CPU 的频率之争，本质上是吞吐量之争。

### 4.3 代价与预告：冒险

上面的美好时空图有一个隐藏假设：相邻指令互不依赖。现实中 `add x5, x6, x7` 后面紧跟 `sub x8, x5, x9` 时，`sub` 在 ID 站读 `x5` 的时刻，前一条 `add` 的结果还在 MEM/WB 站里没写回——读到的是旧值。这叫**数据冒险**；分支指令到 EX 站才知道跳不跳，此前取的指可能是错的，这叫**控制冒险**。它们不是流水线的 bug，而是"多条指令同时在厂"的必然产物，有系统化的解法（转发、停顿、预测）——这是下一章的全部内容，第 15 章见。

## 5. 小结

| 主题 | 要点 |
|---|---|
| RV32I 设计哲学 | load-store、定长、字段对齐——为硬件规整性服务 |
| 单周期数据通路 | PC → 取指 → 译码/读堆 → ALU → 访存 → 写回，四个多选器对应指令差异 |
| 控制器 | 主译码器（opcode → 控制信号）+ ALU 译码器（funct → ALU 操作），两张小真值表 |
| 单周期病根 | 时钟周期 = 最慢指令（lw）的路径；快指令陪跑，部件大量闲置 |
| 五级流水 | IF/ID/EX/MEM/WB + 四个流水线寄存器；控制信号随指令逐级传递 |
| 加速比账 | 吞吐量由最慢站决定；站间不平衡与寄存器税使实际加速 < 5 |
| 遗留问题 | 数据/控制冒险 → 第 15 章 |

一句话收束：**单周期处理器证明了"CPU 就是数据通路加真值表"，五级流水则证明了"吞吐量可以用触发器买"——把长链切成段、让多条指令同时在厂，代价是段间的寄存器税和全新的冒险问题。**

## 自检问题

**1.** 把 `add x5, x6, x7` 手工编码为 32 位 RV32I 机器码（R 型：`add` 的 opcode = `0110011`，funct3 = `000`，funct7 = `0000000`），给出十六进制结果，并说明字段对齐给译码硬件省了什么。

<details markdown="1"><summary>点击显示答案</summary>

逐字段填入（rs1 = `x6` = `00110`，rs2 = `x7` = `00111`，rd = `x5` = `00101`）：

| funct7 | rs2 | rs1 | funct3 | rd | opcode |
|---|---|---|---|---|---|
| 0000000 | 00111 | 00110 | 000 | 00101 | 0110011 |

拼接：0000000 00111 00110 000 00101 0110011，按 4 位分组

$$0000\ 0000\ 0111\ 0011\ 0000\ 0010\ 1011\ 0011 = \texttt{0x007302B3}.$$

字段对齐的收益：`rs1`、`rs2`、`rd` 在所有格式里占据固定比特位（19–15、24–20、11–7），寄存器堆的读地址可以**不经译码直接连线**，ID 站一开始就能读寄存器堆——即使随后译码发现该指令不用 rs2（如 `lw`），白读一次也无副作用。这把"译码"和"读堆"从串行变成并行，直接缩短 ID 站延迟；opcode 固定在低 7 位同理，主译码器的输入位置恒定。

</details>

**2.** 用第 3.4 节的延迟参数，(a) 验证 `lw` 是单周期处理器的关键路径指令并算出最高频率；(b) 有人提议"给 `add` 这类快指令用短周期、`lw` 用长周期"，即每条指令配自己的时钟周期——用第 6 章的同步设计纪律说明这条路为什么走不通。

<details markdown="1"><summary>点击显示答案</summary>

**(a)** 各指令路径（多选器延迟忽略）：

- `add`：$0.05 + 0.20 + 0.15 + 0.20 + 0.05 = 0.65$ ns；
- `sw`：$0.05 + 0.20 + 0.15 + 0.20 + 0.25 = 0.85$ ns；
- `lw`：$0.05 + 0.20 + 0.15 + 0.20 + 0.25 + 0.05 = 0.90$ ns——唯一走满"取指、读堆、ALU、访存、写回"五段的指令，确为最长。

$T_c \ge 0.90$ ns，$f_{max} = 1/0.90 \approx 1.11$ GHz。

**(b)** "每条指令自己的周期"意味着**可变长度时钟**或**多个时钟域**。前者：时钟周期变成数据依赖的量，时钟网络上要挂"本拍该多长"的组合逻辑——这正是第 6 章规则三禁止的"用逻辑造时钟"，建立/保持分析的前提（固定 $T_c$）不复存在，STA 无从下手。后者：指令间切换时钟域，跨域信号全是异步的，每个寄存器堆写口都要过同步器，数据通路被 MTBF 问题淹没。同步设计的方法论红利——"时序 = 逐条触发器到触发器路径查两个不等式"——恰恰来自"所有人听同一个节拍"。单周期机正确的出路不是给指令配时钟，而是承认指令执行时间天然不同，改用**多周期**（FSM 分拍）或**流水**（本章）结构，在单一时钟内消化这个差异。

</details>

**3.** 用第 4.2 节的站延迟表，(a) 求五级流水机的时钟周期与理想吞吐量加速比（相对第 2 题的单周期机）；(b) 若把 MEM 站再切成 MEM1/MEM2 两段（各约 0.175 ns，外加寄存器税 0.10 ns），新机器快多少？这说明了什么规律？

<details markdown="1"><summary>点击显示答案</summary>

**(a)** 各站延迟：IF 0.30、ID 0.25、EX 0.30、MEM 0.35、WB 0.10 ns。时钟周期由最慢站决定：$T_c = 0.35$ ns，$f_{max} \approx 2.86$ GHz。流水线灌满后每 0.35 ns 流出一条指令，吞吐量加速比

$$\frac{0.90}{0.35} \approx 2.6\times.$$

**(b)** MEM 切成两段后各段延迟为 $0.175 + 0.10 = 0.275$ ns，此时最慢站变成 IF/EX 的 0.30 ns，$T_c = 0.30$ ns。新加速比 $0.90/0.30 = 3.0\times$，相对改进只有 $0.35/0.30 \approx 17\%$——**多付了一整级流水线寄存器，只买了 17%**。

规律有二：其一，流水线的收益被**次慢站**卡住，砍掉最长的段之后瓶颈立刻换人（IF/EX），继续细分必须全线均衡地切；其二，每多一级，每段都要重付 $t_{pcq} + t_{setup} = 0.10$ ns 的寄存器税，段越短税占比越高（本例 0.275 ns 里税占 36%）。收益递减 + 税递增，两线相交处就是流水级数的最优点——这也是工业界处理器收敛到 10–20 级而非无限细分的定量原因。

</details>

**4.** 指令 `lw x5, 40(x6)` 流过五级流水线。逐站说明它做了什么、各流水线寄存器必须为它携带哪些信息，并指出：如果设计者忘了把 RegWrite 和写地址 `rd` 逐级传到 WB 站，会发生什么。

<details markdown="1"><summary>点击显示答案</summary>

- **IF**：从指令存储器读出 `lw` 的机器码；IF/ID 寄存器保存指令字与 PC+4。
- **ID**：译码出全部控制信号；读 `x6`（地址基值）；立即数生成器产出符号扩展的 40；`rd = x5` 编号从指令字段取出。ID/EX 寄存器保存：`x6` 的值、立即数、`rd` 编号、以及控制信号（RegWrite = 1、MemtoReg = 1、ALUSrc = 1、ALUOp = 00）。
- **EX**：ALU 算 $x6 + 40$ 得访存地址。EX/MEM 寄存器保存：地址、`rd` 编号、以及 MEM/WB 站还要用的控制信号（RegWrite、MemtoReg、MemRead）。
- **MEM**：按地址读数据存储器，得到要装载的字。MEM/WB 寄存器保存：读出的数据、`rd` 编号、RegWrite、MemtoReg。
- **WB**：MemtoReg = 1 选存储器数据，RegWrite = 1 把它写入 `x5`。

如果 RegWrite 没有随车传到 WB：WB 站的写使能只能来自"当前正在 ID 站译码的那条指令"——写不写、写哪里由**别人**决定，`lw` 的结果可能丢失，更可能把无辜指令的控制信号错配到它头上。如果 `rd` 编号没有逐级传递：WB 站同样只能看到当前 ID 站指令的 `rd` 字段，数据会写进**错误的寄存器**。这类 bug 的隐蔽之处在于流水线灌满前（前 4 拍）一切看起来正常，只有多条指令在厂时才爆雷——这正是"控制信号是贴在工件上的工序卡"的含义：工件流到哪个站，工序卡必须跟到哪个站。

</details>

**5.** 第 4.2 节算出五级流水的吞吐量加速约 2.6 倍，但单条指令的延迟从 0.90 ns 增加到 1.75 ns。既然每条指令变慢了，为什么说流水线"更快"？请分清延迟与吞吐量两个指标，并各举一个"延迟重要"和"吞吐量重要"的真实场景。

<details markdown="1"><summary>点击显示答案</summary>

**延迟（latency）**：一条指令从取指到写回的时间，单周期 0.90 ns → 五级流水 $5 \times 0.35 = 1.75$ ns，确实变长（流水线寄存器税 + 站间不平衡）。**吞吐量（throughput）**：单位时间完成的指令数，0.90 ns 一条 → 0.35 ns 一条，提升 2.6 倍。两者不矛盾：流水线里没有一条指令变快，但**在制品**从 1 条变成 5 条。工厂类比：一辆汽车过装配线从进厂到出厂的时间变长了，但出厂线上每小时开下的车变多了。

CPU 为什么押吞吐量：程序是指令的**流**，绝大多数指令的结果不急着立刻被使用（或者通过第 15 章的转发机制，在厂内就能被后继指令取走，不必等写回）。衡量处理器性能的标准程序是"跑完这段基准测试要几秒"，测试的总指令数固定，时间 = 指令数 × CPI × $T_c$——流水线压的是 $T_c$，CPI 近似不变（理想为 1），总时间随吞吐量线性缩短。

**延迟重要的场景**：实时控制回路——电机控制器每 100 μs 必须完成一次"采样 → 计算 → 输出"，单次计算的延迟直接决定控制带宽与稳定性，流水线吞吐再高，单拍延迟超标就是不合格；人机交互的"点击到响应"同理。**吞吐量重要的场景**：视频编码、科学计算、AI 训练——海量数据过同一段程序，单条数据何时算完无所谓，总吞吐就是一切（这也是 GPU 把流水线与并行度推向极致、完全不管单线程延迟的原因）。通用 CPU 站在中间：用流水线买吞吐，再用乱序、转发、分支预测把"延迟偶尔咬人"的代价压回去。

</details>
